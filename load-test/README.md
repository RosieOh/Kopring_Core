# 부하 테스트 — 즉시 발급 vs 대기열

오픈 순간 사용자가 한꺼번에 몰릴 때, 두 발급 방식이 **어디서 버거워지는지**를 숫자로 비교합니다.
처음 잰 결과(M3)에서 찾은 병목 세 가지를 M4 에서 고치고, 같은 조건으로 다시 재서 전후를 비교했습니다.

| 방식 | 흐름 (M4) |
|---|---|
| 즉시 발급 (`DIRECT`) | 요청 → 사전 검사(메모리 캐시) → **원자적 UPDATE**(기본) 또는 Redis 분산락으로 DB 발급 → 응답 |
| 대기열 (`QUEUE`) | 요청 → Redis 에 줄 서기 → 202 응답 / 워커가 50명씩 한 트랜잭션으로 발급하고, 줄이 남아 있으면 쉬지 않고 이어서 처리 / 사용자는 서버가 알려준 간격(`retryAfterMillis`, 0.3~3초)마다 조회하거나 SSE 로 결과를 받음 |

## 실행

```bash
docker compose --profile monitoring up -d   # MySQL·Redis + Prometheus·Grafana
./gradlew bootRun                             # local 프로필 (즉시 발급: 원자적 UPDATE)
./load-test/run-comparison.sh                 # 100·500·1000·2000명, 쿠폰 100장, 두 방식 → results/summary.md

# 조건 바꾸기
VUS_LIST="2000 5000" QUANTITY=1000 ./load-test/run-comparison.sh
SCENARIOS=direct LABEL=lock ./load-test/run-comparison.sh        # 한 방식만, 결과는 results/lock/
POLL_MODE=fixed SCENARIOS=queue ./load-test/run-comparison.sh    # 0.5초 고정 조회 (개선 전 클라이언트)

# 즉시 발급을 분산락으로 재려면 앱을 다시 띄운다
./gradlew bootRun --args='--coupon.issue.direct-strategy=distributed-lock'
```

실행 중에는 Grafana(http://localhost:3000)의 "Kopring Core — 선착순 쿠폰" 대시보드에서 서버 쪽 변화를 볼 수 있습니다.

## 방법

- **모든 가상 사용자(VU)가 같은 순간에 출발**해 1번씩 요청합니다. (`per-vu-iterations`, 오픈 순간 몰림 재현)
- **토큰은 k6 가 직접 서명**합니다. 회원 수천 명을 가입·로그인시키면 bcrypt 비용 때문에 준비에 수 분이 걸리고 그 부하가 측정에 섞입니다. 서버는 서명·만료만 검증하고 발급은 회원 존재 여부를 따지지 않으므로, 회원 ID 별로 서명한 토큰이면 충분합니다. (로컬 전용 키 사용)
- 대기열 사용자는 결과를 60초까지 기다리고, 그 안에 못 받으면 "시간 초과"로 셉니다.
- 서버 지표(DB 커넥션 대기, Tomcat 스레드, 락 대기 p95, 대기열 인원)는 실행 구간 동안 Prometheus 가 1초마다 수집한 값입니다.
- 실행마다 워밍업(200명)을 먼저 돌려 JIT 영향을 뺐습니다.
- **개선 전은 M3 코드(main `2623813`)를 같은 날 같은 기계에서 따로 띄워** 쟀습니다. 기록해 둔 옛 숫자가 아니라 나란히 다시 잰 값입니다.

환경: Apple M4 (10코어, 24GB) 한 대에서 k6·앱·MySQL·Redis 를 함께 실행 / k6 2.2.0 / JDK 21 / MySQL 8.4·Redis 7.4 (Docker) / Tomcat 스레드 200, DB 커넥션 풀 10 (기본값)

## 해석

**1. 즉시 발급 — 캐시 사전 검사는 "덜 막히게", 원자적 UPDATE 는 "더 빨리".**
사전 검사를 메모리로 옮기자 소진 뒤 요청은 DB·락 없이 바로 돌아가고, 개선 전 1,000·5,000명에서 66까지 쌓였던 커넥션 대기가 분산락 방식에서 0 이 됐습니다.
하지만 응답 시간은 조금만 줄었습니다(1,000장 · 2,000명 4.77s → 4.32s). 분산락은 발급 한 건마다 "락 획득 → 트랜잭션 → 커밋 → 락 해제"를 차례로 거치고, 쿠폰이 남아 있는 동안의 요청은 모두 이 줄에 서기 때문입니다.
원자적 UPDATE 는 줄 서는 구간이 "행 잠금 → 발급 내역 INSERT → 커밋" 뿐이라 **모든 조건에서 개선 전보다 2.4~2.6배 빨랐습니다.**

**2. 원자적 UPDATE 의 대가는 DB 커넥션입니다.**
행 잠금을 기다리는 요청은 DB 커넥션을 쥔 채 기다립니다. 1,000장 · 2,000명에서 커넥션을 얻으려고 기다린 요청이 110 까지 쌓였습니다(분산락은 기다림이 Redis 에서 일어나 0).
이 기능이 DB 를 거의 혼자 쓴다면 문제없지만, 같은 DB·커넥션 풀을 쓰는 다른 API 가 있다면 그 API 가 같이 느려집니다. 그래서 방식을 설정(`coupon.issue.direct-strategy`)으로 남겼습니다.

**3. 대기열 — 처리량이 6.5배, 요청 수는 1/6.**
워커가 한 명씩 트랜잭션을 열던 것을 50명씩 한 트랜잭션으로 바꾸고, 줄이 남아 있으면 쉬지 않고 이어서 처리하게 했습니다. 1,000장을 다 나눠 주는 시간이 12.19s → 1.86s 가 됐습니다.
기다리는 시간이 줄어든 데다 조회 간격 힌트(앞 순번은 짧게, 뒤 순번은 길게)까지 더해져, 같은 실행의 HTTP 요청이 38,412 → 6,163 으로 줄었습니다.

**4. 5,000명에서 개선 전 대기열은 무너졌습니다.**
0.5초마다 묻는 5,000명이 초당 수천 건의 조회를 만들었고, 같은 기계에서 워커와 자원을 다퉈 발급이 더 느려지는 악순환이 생겼습니다. 4,234명이 60초 안에 결과를 받지 못했고 요청은 38만 건이 넘었습니다.
개선 후에는 같은 조건에서 시간 초과 없이 모두 결과를 받았습니다. (p95 7.12초, 요청 22,033건)

**5. 쿠폰이 적을 때는 힌트가 결과를 조금 늦게 알려 줍니다.**
100장 · 2,000명에서 개선 후 p95(2.38s)가 개선 전(1.87s)보다 깁니다. 힌트는 "초당 500명 처리"를 가정해 2,000번째 사용자에게 2초 뒤에 다시 물으라고 하는데,
실제로는 100장이 금방 소진되고 워커가 나머지 1,900명을 곧바로 한꺼번에 정리합니다. 결과는 이미 나왔는데 다음 조회 때까지 모르는 것입니다. SSE 를 쓰면 정리되는 순간 받습니다.

**6. 이제 두 방식의 차이는 "속도"보다 "무엇을 지키느냐"입니다.**
1,000장 · 2,000명에서 즉시 발급(원자적 UPDATE) 1.92s, 대기열 1.86s 로 결과까지 시간이 비슷해졌습니다. 차이는 DB 커넥션 대기(110 vs 0)입니다.
5,000명에서는 즉시 발급이 더 빨랐지만(2.27s vs 5.59s), 대기열은 몰림이 얼마나 커지든 DB 에 가는 부하가 워커 속도로 고정됩니다.

## 그래서 언제 무엇을 쓰나

| 상황 | 추천 |
|---|---|
| 사용자가 즉시 결과를 원하고, 이 기능이 DB 를 거의 혼자 쓸 때 | 즉시 발급 + 원자적 UPDATE (기본) |
| 즉시 결과가 필요하지만 같은 DB 를 다른 기능과 함께 쓸 때 | 즉시 발급 + 분산락 — 2배쯤 느리지만 DB 커넥션을 붙잡고 기다리지 않음 |
| 몰리는 인원이 아주 크거나 예측하기 어려울 때, 줄 선 순서대로 주는 게 중요할 때 | 대기열 — DB 부하가 워커 속도로 고정 |

## 개선 여지

- **남은 수량을 아는 힌트**: 순번이 남은 수량보다 뒤인 사용자는 "소진되는 순간"(남은 수량 ÷ 처리량) 결과가 나옵니다. 힌트를 순번 대신 `min(순번, 남은 수량)` 으로 계산하면 해석 5의 지연이 사라집니다.
- **즉시 발급의 커넥션 점유**: 원자적 UPDATE 를 쓰면서 다른 API 를 지키려면 요청 수 제한(rate limit)이나 발급 전용 커넥션 풀로 나눌 수 있습니다.
- **오픈 순간의 Tomcat 스레드**: 5,000명이 동시에 줄을 서면 등록이 Redis 몇 번 왕복으로 끝나는데도 스레드 200개가 잠깐 찹니다. 가상 스레드(`spring.threads.virtual.enabled`)로 스레드 수 제한을 없애는 것을 검토할 수 있습니다.

## 한계

- k6·앱·DB 가 한 대에서 자원을 나눠 썼습니다. 서버를 분리하면 절대값은 달라집니다. 이 문서는 같은 조건에서 방식끼리 **상대 비교**한 것입니다.
- 같은 조건이라도 실행마다 10~15% 흔들립니다. (예: 대기열 개선 전 1,000장 · 2,000명을 두 번 재서 14.23s, 12.19s)
- 서버 지표는 1초 간격 표본이라 1초보다 짧은 순간 최대치는 놓칠 수 있습니다. 1초 안에 끝난 실행의 Tomcat 스레드·커넥션 대기가 0~2 로 나온 것이 그 예입니다.
- `bootRun` 은 시작을 빠르게 하려고 JIT 를 C1 까지만 씁니다(`-XX:TieredStopAtLevel=1`). 운영(jar 실행)보다 느리지만 모든 실행이 같은 조건입니다.
- 회원 레코드 없이 토큰만으로 요청해서 발급 알림은 모두 `SKIPPED` 로 끝났습니다. 실제 알림 발송 비용은 들어 있지 않습니다.
