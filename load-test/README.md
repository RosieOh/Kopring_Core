# 부하 테스트 — 즉시 발급 vs 대기열

오픈 순간 사용자가 한꺼번에 몰릴 때, 두 발급 방식이 **어디서 버거워지는지**를 숫자로 비교합니다.

| 방식 | 흐름 |
|---|---|
| 즉시 발급 (`DIRECT`) | 요청 → 사전 검사 → Redis 분산락 → DB 발급 → 응답 |
| 대기열 (`QUEUE`) | 요청 → Redis 에 줄 서기 → 202 응답 / 워커가 200ms 마다 50명씩 DB 발급 / 사용자는 0.5초마다 결과 조회 |

## 실행

```bash
docker compose --profile monitoring up -d   # MySQL·Redis + Prometheus·Grafana
./gradlew bootRun                             # local 프로필
./load-test/run-comparison.sh                 # 100·500·1000·2000명, 쿠폰 100장 → results/summary.md
VUS_LIST="2000" QUANTITY=1000 ./load-test/run-comparison.sh
```

실행 중에는 Grafana(http://localhost:3000)의 "Kopring Core — 선착순 쿠폰" 대시보드에서 서버 쪽 변화를 볼 수 있습니다.

## 방법

- **모든 가상 사용자(VU)가 같은 순간에 출발**해 1번씩 요청합니다. (`per-vu-iterations`, 오픈 순간 몰림 재현)
- **토큰은 k6 가 직접 서명**합니다. 회원 수천 명을 가입·로그인시키면 bcrypt 비용 때문에 준비에 수 분이 걸리고 그 부하가 측정에 섞입니다. 서버는 서명·만료만 검증하고 발급은 회원 존재 여부를 따지지 않으므로, 회원 ID 별로 서명한 토큰이면 충분합니다. (로컬 전용 키 사용)
- 서버 지표(DB 커넥션 대기, Tomcat 스레드, 락 대기 p95, 대기열 인원)는 실행 구간 동안 Prometheus 가 1초마다 수집한 값입니다.
- 첫 실행 전에 워밍업(200명)을 한 번 돌려 JIT 영향을 뺐습니다.

환경: Apple M4 (10코어, 24GB) 한 대에서 k6·앱·MySQL·Redis 를 함께 실행 / k6 2.2.0 / JDK 21 / MySQL 8.4·Redis 7.4 (Docker) / Tomcat 스레드 200, DB 커넥션 풀 10 (기본값)

## 결과 2 — 쿠폰 1,000장, 2,000명

| 방식 | 발급 | 소진 | 실패 | 사용자가 결과를 받기까지 (중앙값 / p95) | 총 HTTP 요청 | DB 커넥션 대기 최대 | Tomcat 스레드 최대 |
|---|---|---|---|---|---|---|---|
| 즉시 발급 | 1,000 | 1,000 | 0 | **4.92s / 5.34s** (응답) | 2,000 | 23 | 172 |
| 대기열 | 1,000 | 1,000 | 0 | **12.05s / 12.55s** (등록 p95 242ms) | 38,001 | 0 | 61 |

원본 표: [results/quantity-100.md](results/quantity-100.md), [results/quantity-1000.md](results/quantity-1000.md)

## 해석

**1. 정합성은 두 방식 모두 지켰습니다.** 모든 실행에서 정확히 쿠폰 수만큼만 발급됐고, 실패·시간 초과는 0건입니다.

**2. 즉시 발급은 요청이 몰리면 "앞단 자원"이 먼저 찹니다.**
500명에서 Tomcat 스레드 200개가 모두 차고 DB 커넥션을 기다리는 요청이 75개까지 쌓였습니다.
쿠폰 1,000장 실험에서는 락 대기 p95(1.27s)보다 응답(약 5s)이 훨씬 길었습니다. 요청이 락에 닿기 전에 **Tomcat 스레드를 얻으려고 줄을 섰다**는 뜻입니다.
응답이 락 대기 한도(5초)에 거의 닿았기 때문에, 조금만 더 몰리면 `LOCK_ACQUISITION_FAILED`(503)가 나기 시작합니다.

**3. 대기열은 DB 를 지키는 대신 "결과를 받기까지의 시간"을 내줍니다.**
DB 커넥션 대기는 모든 실행에서 0입니다. 줄 서기 응답도 빠릅니다(p95 0.04~0.27초).
대신 워커가 한 명씩 차례로 발급하므로 **처리량이 DB 왕복 시간에 묶입니다.** 1,000장을 다 나눠 주는 데 약 12초가 걸렸습니다. 이 환경에서 워커 하나는 초당 100건 안팎을 처리한 셈입니다.

**4. 대기열의 숨은 비용은 상태 조회(폴링)입니다.**
기다리는 동안 0.5초마다 조회해서, 결과까지 12초가 걸린 실행에서는 HTTP 요청이 사용자당 약 19건(총 38,001건)으로 불었습니다.
2,000명 · 100장 실행에서는 한꺼번에 들어온 줄 서기와 이어지는 조회로 Tomcat 스레드가 잠깐 찼습니다. 다만 둘 다 Redis 만 쓰는 요청이라 DB 커넥션 대기는 0 이었습니다.

## 그래서 언제 무엇을 쓰나

| 상황 | 추천 |
|---|---|
| 수량이 적고(수백 장) 사용자가 즉시 결과를 원할 때 | 즉시 발급 — 이 규모에서는 락 타임아웃 없이 1~1.4초 안에 응답 |
| 몰리는 인원이 Tomcat 스레드·DB 커넥션 풀보다 훨씬 클 때, DB 를 다른 기능과 함께 쓸 때 | 대기열 — DB 부하를 워커 속도로 고정 |

## 개선 여지

- **대기열 처리량**: 워커가 회원을 한 명씩 발급합니다. 배치 INSERT, 또는 워커 여러 개로 늘리면 빨라집니다(엄격한 순서는 조금 느슨해짐).
- **폴링 비용**: 조회 간격을 순번에 따라 늘리거나(앞 순번은 짧게, 뒤 순번은 길게), SSE 로 결과를 밀어 주면 요청 수가 크게 줍니다.
- **즉시 발급**: 사전 검사가 소진 이후 요청은 빨리 돌려보내지만, 소진 전 요청은 모두 락에 줄을 섭니다. 요청 수 제한(rate limit)이나 Tomcat 스레드·커넥션 풀 조정이 필요합니다.

## 한계

- k6·앱·DB 가 한 대에서 자원을 나눠 썼습니다. 서버를 분리하면 절대값은 달라집니다. 이 문서는 같은 조건에서 두 방식을 **상대 비교**한 것입니다.
- 서버 지표는 1초 간격 표본이라 1초보다 짧은 순간 최대치는 놓칠 수 있습니다. (1,000·2,000명 즉시 발급에서 DB 커넥션 대기가 0 으로 나온 것이 그 예일 수 있습니다)
- 결과까지 시간에는 조회 간격(0.5초) 단위의 오차가 있습니다.
- 회원 레코드 없이 토큰만으로 요청해서 발급 알림은 모두 `SKIPPED` 로 끝났습니다. 실제 알림 발송 비용은 들어 있지 않습니다.
